# 実装計画の評価方法 (prepare__issue)

`prepare__issue` スキルが親 Issue 更新前に skeptical-reviewer へ注入する評価方法である。
issue-preparer が返した調査・計画レポートを、対象リポジトリの実コードと突き合わせて反証する。

## 評価の姿勢

- 計画の主張・前提が成立しない可能性のある箇所だけを挙げる
- 提案手法の記述 (パス・既存構造・diff の前提) は、リポジトリの実コードで裏取りを試みる
- 裏取りできない指摘は根拠に「未検証」と明記し、推測で断定しない

## 評価観点

| 観点 | 検査内容 |
|---|---|
| 実コードとの整合 | 変更対象ファイルが実在する。diff の変更前コードが現状と一致する。参照される既存のインターフェース・設定・類似実装が実在する |
| 見落とし | 提案手法が再発明していないか。既存の拡張点・ユーティリティで置き換えられる箇所がないか |
| 受入基準の計測可能性 | 各項目が技術観点で客観的に検証できる。「正しく動く」「問題なく動作する」のような計測不能な表現がない |
| SP の整合 | 親 Issue の SP がサブイシューの SP 合計と一致する。7 SP を超えるサブイシューがない (1 SP = 人間の実装 1 時間) |
| 分割の妥当性 | 各サブイシューが 1 PR で完結する粒度である。依存関係が実装順として成立し (循環がない)、並行可否の記載と矛盾しない |
| 図の整合 | ロジックフロー (分岐・失敗レールを含む) とコンポーネント関係の図が、提案手法の記述・依存方向と矛盾しない |
| ヒアリング結論の反映 | 採用アプローチ・スコープ境界・粒度感が Phase 2 の結論と一致する。範囲外とされた作業が紛れ込んでいない |
| 要件定義の保持 | acknowledged 時点の要件定義セクション (概要〜目標) を書き換える前提になっていない |

## 出力形式 (本評価方法が指定する)

既定の反証表 (指摘 / 深刻度 / 根拠 / 確度) で出力する。
末尾の「反証を試みたが壊せなかった点」に続けて、次の判定行を追加する。

- `Verdict: pass` — 深刻度が高または中の指摘が 0 件の場合
- `Verdict: needs_fix` — 深刻度が高または中の指摘が 1 件以上の場合
