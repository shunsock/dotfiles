# コメントマーカー語彙 (共有)

`write__structured_comment` (書く) と `clean__comment_out` (掃除する) が共有する
single source of truth。両スキルはこのファイルのマーカー語彙・フォーマット・契約を
参照する。ここを変えれば両スキルの挙動が同時に変わり、契約のずれ (drift) が起きない。

このファイルは人間・スキル向けの意味定義であり、両スキルはこれを読む。機械可読な
語彙は検証フック `validate_comment_format.cs` 内の const (正規表現) が持つ。読者が
この 1 フックだけなので外部ファイルに切り出さず const とした。このファイルと const は
必ず同じ 7 マーカーを保つこと。

## 原則 — デフォルトはコメント 0

コードはプログラム知識を naming / types / structure で表現する。ドメイン知識は
ドメインモデル (型) で定義する。したがって **プログラム知識・ドメイン知識を説明する
コメントは書かない** (書きたくなったらコードを直す)。

コメントが正当化されるのは、コードに表現できない知識 — **未完の事実**・
**外部世界の事実**・**人間が明示的に残せと指示した知識** — だけ。デフォルトは
コメント 0 とし、以下のマーカー語彙だけを whitelist として開ける。

## マーカー語彙 (7)

### 未完の記録 — コードが意図的に不完全だと我々が知っている

| marker | これを書く条件 |
|---|---|
| `TODO` | 計画済みだが未実装 |
| `FIXME` | 既知の不具合 |
| `HACK` | 意図的な醜い回避策。「ミスと思って直すな」と読み手に伝える |

### 外部事実への参照 — コードに住めない外部世界を指す

| marker | これを書く条件 |
|---|---|
| `SEE` | 外部権威 (RFC / 仕様 / ベンダー doc / 関連ファイル) へのポインタ。内容は**ファイルパスまたは URL のみ**とし、散文を付けない。**issue / PR 番号・issue / PR の URL は書かない** (下記参照) |
| `CONSTRAINT` | 他システムの実行時挙動による制約 (レート制限・ベンダーバグ 等) |
| `SAFETY` | `unsafe` の健全性根拠 (型で検証不能な、人間が担保する不変条件) |

### 人間の明示指示 — ユーザーが残せと指示した知識

| marker | これを書く条件 |
|---|---|
| `NOTE` | **ユーザーが明示的にこのコメントを入れろと指示したときだけ** 使う escape hatch。モデルが自律判断で足してはならない。他マーカーに該当しないコメントをユーザーが要求した場合の唯一の受け皿 |

これら以外の理由でコメントを書きたくなったら、それは次のいずれかである:

- **コードを直すシグナル** — 命名・型・構造で表現できる (= プログラム知識)。
  ドメインの事実ならドメインモデルで定義する (= ドメイン知識)。
- **commit / PR に書くべき一過性の経緯** — このコードが在る限り恒久的に真ではない。

`Domain` を語彙に含めないのはこのため。我々の業務規則は型でモデル化すべきものであり、
コメントへ逃がしてはならない。`CONSTRAINT` が残るのは、それが **他システム** の挙動で
あって我々のコードでは型にできない外部事実だからである。`NOTE` は例外の逃げ道だが、
起動条件を「ユーザーの明示指示」だけに縛ることで汎用 Why の穴になるのを防ぐ。

## フォーマット (機械的に強制する)

対象言語のコメント構文でレンダリングする (`//`, `#`, `--` 等)。以下の制約は
`validate_comment_format.cs` が違反を検出して修正を強制する。

- **語彙必須**: すべてのコメントは whitelist の 7 マーカーのいずれかで始める。
  マーカーで始まらないコメントは書かない (掃除側で削除される)。
- **1 論理コメントは最大 2 行**。3 行以上に渡るコメントは禁止。書ききれないなら、
  それはコメントに収める知識ではない (コードを直す / モデル化する / 履歴に残す)。
- **1 行は最大 80 文字**。超えるなら短く簡潔に言い換える。
- **改行は文末 (句点) でのみ行う**。文の途中で折り返さない (例: 「〜のため」で改行して
  次行へ続けるのは禁止)。1 文が 80 文字に収まらないなら、途中で折り返さず短い文に分ける。
- **issue / PR 番号を書かない**。`#123`・`GH-123`・`issues/123`・`pull/123`・
  issue / PR の URL はすべて禁止。issue / PR は一過性の経緯であり commit / PR 本文に
  属す。コードに恒久的に残す外部参照 (`SEE`) は RFC・仕様・ベンダー doc・
  ファイルパスに限る。
- インライン: `MARKER: content` (1 行に収める)。
- 複数行: `MARKER:` の次行に本文 1 行 (合計 2 行まで)。各行にコメント記号を付ける。

例 (Rust):

```rust
// CONSTRAINT: 上流 API は 10 req/s でレート制限される
sleep(Duration::from_millis(120));

// SAFETY:
// ptr は直前の alloc で非 null かつ len バイトは同一アロケーション内で有効
unsafe { slice::from_raw_parts(ptr, len) }
```

例 (Python):

```python
# SEE: https://www.rfc-editor.org/rfc/rfc1234#section-4.2
# TODO: タイムアウトを設定から注入する
```

公開インターフェースのドキュメンテーションコメント (rustdoc `///`、JSDoc、docstring)
はこのマーカー語彙の対象外。言語ネイティブの doc 機構で書き、型・名前で表現できる
情報を重複させない。検証フックも掃除スキルも doc コメントは例外として扱う。

## 2 スキル間の契約 (対称・厳格)

- **writer (`write__structured_comment`) の出力集合** = 上記 7 マーカーちょうど。
  これ以外のコメントを生成しない。すべて 2 行・80 文字・issue/PR 番号禁止に従う。
- **cleaner (`clean__comment_out`) の保持集合** = 7 マーカー + doc コメントちょうど。
  whitelist マーカーで始まらない非 doc コメント (What コメント・汎用 Why・
  デッドコード・legacy `XXX` 等) は**すべて削除する**。
- 帰結: **writer が書いたコメントに cleaner をかけても no-op になる** (掃除人は
  書き手の出力を消さない)。両者が同じ whitelist を厳格に共有し、doc コメントだけを
  共通の例外とする — この対称が正しい関係である。
